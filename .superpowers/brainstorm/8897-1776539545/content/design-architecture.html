Design — Section 1: Architecture

How the new Spatial Generator module fits into the existing agent pipeline

System Architecture
User Query
"Generate Voronoi zones for all hospitals and show coverage gaps"
Agent Orchestrator
ReAct loop — thinks, picks tools, observes results
Frontend Map
Renders GeoJSON layers from agent response
TOOL_REGISTRY (agent_tools.py) — existing + new
Existing (11 tools)
geocode_location, create_buffer,
execute_sql, calculate_route,
walking_isochrone, score_locations…
New (~12 tools)
generate_voronoi, generate_hexgrid,
site_suitability, coverage_gaps,
kernel_density, add_hypothetical,
compare_scenarios, equity_gap_analysis…
NEW: spatial_generator.py
Pure Shapely + GeoPandas computation.
No DB access directly — returns GeoJSON.

voronoi_from_points()
hexagonal_grid()
kernel_density_grid()
suitability_score()
coverage_gap_detect()
PostGIS — temp_layers schema
Generated features saved as named layers.
Reuses existing pattern already in DB.

temp_layers.layer_voronoi_hospitals_*
temp_layers.layer_hexgrid_berlin_*
temp_layers.layer_scenario_a_clinic_*

→ Agent can query them in follow-up turns
Data flow: Query → Agent picks tool → Tool fetches from PostGIS → spatial_generator.py computes → GeoJSON returned → Agent saves to temp_layers → Frontend renders layer + Agent can reference it in next query

Does this architecture make sense? The key idea: spatial_generator.py is pure computation (no DB), and the tools in agent_tools.py wire it to PostGIS fetch + save.
